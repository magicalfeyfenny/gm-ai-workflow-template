Use the governed-change skill for this repository.

This is a scheduled run. The skill's direct-request issue-creation permission
does not apply.

Before modifying repository state, inspect live open GitHub issues and any
existing incomplete governed work. Before selecting a new issue, first inspect
for an existing continuation and resume it under
[Scheduled continuation](../../GOVERNANCE.md#scheduled-continuation). If a
continuation is actionable because the current environment can make meaningful
progress on at least one remaining implementation or validation milestone, do
not select new work in the same run. If it is pending only for unavailable
required runtime evidence that the accepted issue contract requires, an
unavailable interactive environment for that contract evidence, or explicit
human action, leave it pending and allow new-issue selection for this run.
Human review, readiness, and merge for a high-risk/manual-path PR are authority
actions, not validation blockers; an agent-authored PR body or handoff cannot
make an otherwise complete continuation pending.

If no actionable continuation exists, select at most one new eligible issue under
[Scheduled claim eligibility](../../GOVERNANCE.md#scheduled-claim-eligibility).

For a new selection, an issue is eligible only when:

- it defines one independently meaningful product or repository outcome under
  Issue authority, with actionable acceptance criteria and bounded scope;
- the current execution environment has the capabilities required to complete
  its primary non-degradable deliverable;
- it is unassigned or assigned to the automation's current user;
- it is not labeled `work:blocked` and has no unresolved dependency;
- it has no existing implementation branch or open pull request;
- it is not human-owned or associated with a `human/*` branch or a
  `human-created` change;
- it requires no release, publication, destructive action, or other fresh
  human authority beyond the governed-change workflow's standing permissions.

Prefer the oldest eligible issue unless explicit priority or dependency data
establishes a different order.

Immediately before starting governed work, recheck every eligibility
condition. If a branch, pull request, blocker, dependency, assignment,
ownership, or authority requirement has changed, report that the candidate is
no longer eligible and stop without modifying repository state.

For a continuation, recheck the matching open issue, issue-numbered work branch,
draft pull request, current ownership, blockers, dependencies, remaining
capability, absence of completion metadata, human authority, and current
actionability under
[Scheduled continuation](../../GOVERNANCE.md#scheduled-continuation) before
resuming it.

If no actionable continuation and no eligible issue exists, do not create a
replacement issue or modify repository state. Report that no candidate was
available and stop.

After selecting or resuming one work item, execute only that issue with the
skill and its routed Governance sections. Refresh `origin/dev`. For new work,
create the governed issue branch. For a continuation, use the existing matching
issue branch and draft pull request; do not recreate the branch. Do not absorb
unrelated fixes.

Do not stop after implementation, a milestone commit, draft PR publication, or
hosted checks. When the complete implementation scope is ready, continue the
same work item through the ordinary completion lifecycle:

1. Re-fetch and reconcile the governing issue before Stage 2. Use the issue
   contract command in [Issue contract evidence](../../GOVERNANCE.md#issue-contract-evidence)
   and record its accepted revision with the validation evidence.
2. Run the required Stage 2 whole-issue local evidence on one unchanged
   candidate: repository policy, relevant tests, the full Python suite, and
   `git diff --check`. Use the repository's
   `tools/ci/run_repository_checks.py` entry point for dependency-sensitive
   checks so the selected interpreter is recorded before execution. Missing,
   failed, stale, or mismatched required evidence
   or the accepted issue-contract revision blocks completion metadata. If a
   native, runtime, or interactive capability is unavailable but only limits
   evidence under the accepted contract and Governance, run all available
   evidence and record that limitation accurately; do not create a human-only
   gate or substitute manual, visual, experiential, or human observation.
3. Freeze the candidate, accepted issue revision, and Stage 2 evidence. Run
   the lifecycle in the
   [adversarial review and adjudication route](../../GOVERNANCE.md#adversarial-review-and-adjudication):
   `python3 tools/ci/adversarial_review_session.py run --packet PACKET --output RESULT --initial`.
   For a continuation, provide its state with `--state STATE`.
4. Follow the review policy and lifecycle decisions in
   [Governance](../../GOVERNANCE.md#adversarial-review-and-adjudication) for
   each candidate and result. The packet's actual risk tier selects the
   configured retry budget: low gets one correction retry, while medium and
   high get two. A handoff artifact never authorizes an autonomous reset; a
   human-authorized new candidate starts a fresh lifecycle.
5. Re-fetch and reconcile the governing issue immediately before the completion
   transition. If the contract changed, establish fresh Stage 2 evidence and a
   fresh review for the revised contract before proceeding.
6. Only after that sequence, add exactly one physical-line `Closes #<issue>`
   line and the applicable completion label: `work:complete` for eligible
   low- or medium-risk work, or `work:review-ready` for high-risk or
   manual-path work.
   Never add completion metadata to an intermediate milestone.
7. After completion metadata is present, obtain fresh Stage 3 exact-head hosted
   evidence for the final PR head, body, labels, and accepted issue contract.
   Stage 3 is not a prerequisite for adding completion metadata, but missing,
   failed, stale, or mismatched Stage 3 evidence blocks readiness and
   auto-merge or the manual handoff.
8. For eligible low- or medium-risk work targeting `dev`, leave the existing
   automatic workflow to mark the PR ready and configure squash auto-merge.
   Do not directly mark ready, merge, bypass rulesets, push protected branches,
   release, or publish. High-risk and manual-path work stops for human review,
   readiness, and merge; those are authority actions, not validation blockers.

Allocate evidence under
[Validation coverage allocation](../../GOVERNANCE.md#validation-coverage-allocation).
If a required interactive machine-verifiable check cannot run, follow
[Interactive runtime validation](../../GOVERNANCE.md#interactive-runtime-validation)
and report the missing capability against the actual completion contract.
Do not invent generic gameplay smoke testing, manual playtesting, subjective
review, human observation, readability or feel review, or experiential
acceptance requirements unless explicit human direction requires that specific
judgment. Missing runtime capability does not authorize a human-observation
substitute. Human merge or publication authority does not create verification
work.

Return:

- selected issue;
- branch;
- draft pull request;
- validation state;
- remaining blocker, missing required evidence, or required human action. For
  high-risk/manual-path work, report human review, readiness, and merge as
  authority actions; report manual, visual, live, or experiential validation
  only when the accepted issue contract explicitly requires it.
